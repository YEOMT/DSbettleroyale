## 아직 모르는 부분

서버는 별도 프로세스지만 **브라우저와 같은 Windows PC**다. CPU 스케줄링/네이티브 I/O 대기/PC 경합을 분리하거나 배제하지 못했다. 이 한 쌍의 순차 시험만으로 렌더러나 특정 함수를 근본 원인으로 확정할 수 없다. `snapshot` 경과시간은 상태 준비·뷰 필터·인코딩을 합친 값이고 CPU109ms는 서버 프로세스 전체 값이다.

부하 동등성을 위해 게임 연결/가상 입력은 두 조건 모두 그대로 두고, 교사·학생2명의 수신 스트림을 별도의 읽기 전용 로컬 relay3개에도 전달했다. A는 Node에서 같은 스트림을 파싱/수신, B는 수정하지 않은 배포 클라이언트가 실제 Pixi/Canvas·UI·예측까지 실행한다(1024×768,DPR2,balanced). B의 neutral 입력은 동일한 가상 입력을 덮거나 추가하지 않는다. **브라우저 처리 전체와 relay 스케줄링을 포함하는 비교이며 순수 GPU 비교가 아니다.** 기존 seed/6종 지속객체/30연결/연장HP/배치 위치/60초의6→5 전환을 재사용했으나, 두 조건을 맞추는 고정 의도 경로는 이전 autopilot의 정확한 재생은 아니다. 첫2명의100ms 발동 *시도*는 서버가 기존 쿨타임/잠금으로 판정한다. 소켓/버전/입력 검증을 우회하지 않았다.
